Exercise 06.1 — Host an Azure Functions tool for a Foundry agent (queue-based)

In this exercise, you provision a complete Standard Setup Microsoft Foundry environment and deploy a serverless Azure Functions custom tool connected through Azure Storage queues. Instead of your application invoking an HTTP endpoint synchronously, the Foundry Agent Service itself coordinates tool calls directly with Azure Queue Storage, providing automated retries, scale-to-zero pricing, and clean network and identity isolation.

You will explore the Infrastructure as Code (Bicep) and project manifest (azure.yaml) files, learn what occurs under the hood during each azd command, deploy the Function, and watch a multi-turn conversation resolve tool calls through cloud queues.

This exercise takes approximately 90 minutes.

Standard Setup Requirement: This exercise uses the Standard Setup pattern in Microsoft Foundry. Basic agent setup is not supported for Azure Functions queue tools because the agent runtime requires queue storage resources and network routing provided exclusively by the capability host in the standard setup.

Task 1: Understand the queue-based tool architecture

Before running commands, examine the difference between traditional function calling (Exercise 06) and this queue-based pattern:

DimensionHTTP Function Calling (Exercise 06)Queue-Based Tool (Exercise 06.1)
CallerYour application client code receives the tool call and executes it.The Foundry Agent Service itself executes the tool call in the cloud.
CommunicationSynchronous REST HTTP. The caller waits for an instant response.Asynchronous messages over Azure Storage queues with built-in retries.
Foundry SetupBasic or Standard setup.Standard Setup only (requires Capability Host).
Security BoundaryHTTP endpoints with keys or bearer tokens.Identity-based access (Microsoft Entra ID) with zero shared keys.
Best ForReal-time UI lookups, instant calculations.Long-running jobs, background processing, resilient enterprise integrations.

The Step-by-Step Message Flow

  1. Model Invocation: When the user asks a question, the LLM decides to call the GetWeather tool and prepares the arguments (e.g. {"location": "Seattle, WA"}).
  2. Input Queue Dispatch: Foundry Agent Service generates a unique CorrelationId, packages the arguments into a JSON payload, and writes it directly to get-weather-input-queue using the Foundry Project's managed identity.
  3. Function Execution: An Azure Storage queue trigger wakes the Azure Function in the Flex Consumption plan. The function parses the payload, executes business logic, and prepares the output.
  4. Output Queue Reply: The function writes its JSON answer to get-weather-output-queue, echoing the exact CorrelationId.
  5. Correlation & Turn Completion: Foundry Agent Service reads the output queue, matches the CorrelationId to the pending turn, feeds the tool output back into the model, and completes the response.

Task 2: Deep dive into the Bicep and YAML files

Navigate to the lab directory labs/06.1-azure-functions-tool to inspect the configuration files that drive this deployment:

cd labs/06.1-azure-functions-tool

1. The azd Manifest: azure.yaml

Open azure.yaml. This file is the schema contract between the Azure Developer CLI and your project:

# yaml-language-server: $schema=https://raw.githubusercontent.com/Azure/azure-dev/main/schemas/v1.0/azure.yaml.json
name: azure-functions-tool-lab
services:
  api:
    project: ./app/
    language: python
    host: function
  • name: Unique project identifier in azd.
  • services.api: Declares an application service named api.
  • project: ./app/: Specifies the directory containing the Function app code (function_app.py, host.json, requirements.txt).
  • language: python: Directs azd to use Python packaging and remote build.
  • host: function: Instructs azd deploy to package this service as an Azure Function App deployment package.

2. The Orchestration Template: infra/main.bicep

Open infra/main.bicep. It is targeted at subscription scope (targetScope = 'subscription') and orchestrates the creation of all resources in structured sequence:

  1. Resource Group (rg): Creates the container holding all regional resources.
  2. User-Assigned Managed Identity (apiUserAssignedIdentity): Created for the Function App so it can authenticate to Azure Storage without storing connection strings.
  3. App Service Plan (appServicePlan): Deploys an FC1 SKU serverless Flex Consumption plan for high elasticity and scale-to-zero compute.
  4. Application Insights & Log Analytics (monitoring): Provides distributed tracing and execution telemetry.
  5. Storage Account & Queues (storage): Provisions the integration storage account and declaratively creates two queues: get-weather-input-queue and get-weather-output-queue.
  6. AI Dependent Resources (aiDependencies):
    • An Azure AI Services account (Foundry Account).
    • A model deployment (e.g. gpt-5.1 or gpt-4.1-mini with GlobalStandard SKU).
    • An Azure AI Search service (Standard tier).
    • An Azure Cosmos DB account for agent enterprise thread and state storage.
    • A dedicated storage account for AI project data.
  7. AI Project (aiProject): Creates the Microsoft Foundry Project workspace inside the AI Services account.
  8. Function App (api): Deploys the Python Flex Consumption Function App and configures its app settings: 
    appSettings: {
  PROJECT_ENDPOINT: aiProject.outputs.projectEndpoint
  STORAGE_CONNECTION__queueServiceUri: 'https://${storage.outputs.name}.queue.${environment().suffixes.storage}'
  STORAGE_CONNECTION__clientId: apiUserAssignedIdentity.outputs.clientId
  STORAGE_CONNECTION__credential: 'managedidentity'
}
  9. Capability Host (aiProjectCapabilityHost) — What makes it a Standard Setup:

    This resource (Microsoft.CognitiveServices/accounts/projects/capabilityHosts) binds the Foundry project to your Cosmos DB, Azure AI Search, and AI Storage. This turns a basic project into a Standard Setup capable of reaching custom storage queues.

  10. RBAC Role Assignments (projectRoleAssignments & rbac):
    • Grants Storage Queue Data Contributor to the Foundry Project's managed identity.
    • Grants Storage Queue Data Contributor to the Function App's user-assigned managed identity.
    • Grants Cosmos DB Built-in Data Contributor on database scope (/dbs/enterprise_memory) so the agent runtime can store version definitions.

3. Parameters: infra/main.parameters.json

Open infra/main.parameters.json. It passes dynamic environment values into main.bicep:

{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "environmentName": { "value": "${AZURE_ENV_NAME}" },
    "location": { "value": "${AZURE_LOCATION}" },
    "principalId": { "value": "${AZURE_PRINCIPAL_ID}" },
    "vnetEnabled": { "value": false },
    "modelName": { "value": "gpt-5.1" }
  }
}

The tokens ${AZURE_ENV_NAME} and ${AZURE_LOCATION} are populated automatically by azd from your active environment.

Task 3: What happens under the hood during azd CLI commands

Understanding the exact execution lifecycle of azd helps troubleshoot cloud deployments:

CommandWhat Happens Behind the Scenes
azd init --template azure-functions-ai-services-agent-python Clones Microsoft's official template repository from GitHub (Azure-Samples/azure-functions-ai-services-agent-python). It automatically downloads azure.yaml, the infra/ folder with all Bicep templates, and the app/ folder with the Python Azure Function code into your directory, then prompts for an environment name.
azd env new <name> Creates a hidden folder .azure/<name>/ and initializes a local .env file. This file holds environment variables (like AZURE_LOCATION and AZURE_SUBSCRIPTION_ID) isolated to this specific deployment.
azd provision
  1. Loads azure.yaml and looks for the infra/ folder.
  2. Reads parameters from .azure/<name>/.env and resolves tokenized values in main.parameters.json.
  3. Compiles the Bicep template (and all referenced Bicep modules) into an ARM JSON template in memory.
  4. Authenticates with Azure Resource Manager and submits a subscription-level deployment.
  5. Polls Azure Resource Manager while resources are provisioned in dependency order.
  6. Extracts all Bicep output variables (e.g. PROJECT_ENDPOINT, STORAGE_CONNECTION__queueServiceUri) and appends them to .azure/<name>/.env.
azd deploy
  1. Reads azure.yaml and locates the api service in ./app/.
  2. Creates a zip package containing function_app.py, host.json, and requirements.txt.
  3. Uploads the zip package to the deployment container in Azure Storage.
  4. Calls the Azure Functions Flex Consumption deployment API to perform a serverless remote build (Oryx) and starts the function host.
azd down --purge
  1. Identifies the resource group created for this environment.
  2. Submits a deletion request to Azure for the entire resource group and all contained resources.
  3. The --purge flag explicitly executes a permanent purge on the Cognitive Services (Foundry) resource, preventing soft-delete retention from holding your regional model TPM quota hostage.

Task 5: Deploy the Function App with azd deploy

Inspect the serverless Python code in app/function_app.py before deploying:

import json
import logging
import azure.functions as func

app = func.FunctionApp()

INPUT_QUEUE = "get-weather-input-queue"
OUTPUT_QUEUE = "get-weather-output-queue"

@app.function_name(name="GetWeather")
@app.queue_trigger(arg_name="msg", queue_name=INPUT_QUEUE, connection="STORAGE_CONNECTION")
@app.queue_output(arg_name="reply", queue_name=OUTPUT_QUEUE, connection="STORAGE_CONNECTION")
def get_weather(msg: func.QueueMessage, reply: func.Out[str]) -> None:
    raw = msg.get_body().decode("utf-8")
    logging.info("Message from agent: %s", raw)

    request = json.loads(raw)
    arguments = request.get("function_args") or request
    location = arguments.get("location", "an unknown place")

    # Custom tool logic: compute simulated temperature
    weather = f"It is {len(location) + 10} degrees and sunny in {location}."

    # CRITICAL: Echo back the exact CorrelationId from the agent request
    answer = {
        "Value": weather,
        "CorrelationId": request["CorrelationId"],
    }
    reply.set(json.dumps(answer))
    logging.info("Reply to agent: %s", json.dumps(answer))

  1. Deploy the function to Azure using azd deploy:

    azd deploy

    Check: Output confirms: SUCCESS: Your application was deployed to Azure in ....

  2. Confirm that the Function App registered the queue trigger in Azure:

    az functionapp function list -g rg-azfn-agent-lab -n YOUR_FUNCTION_APP_NAME --query "[].{name:name, trigger:config.bindings[0].type}" -o table

    Check: Displays one row: GetWeather with trigger type queue.

Task 7: Build the agent script with AzureFunctionTool

Inspect ask_the_agent.py in the lab directory:

  1. Tool Definition: Maps the queue names and input schemas:

    def describe_the_tool():
    return AzureFunctionTool(
        azure_function=AzureFunctionDefinition(
            input_binding=AzureFunctionBinding(
                storage_queue=AzureFunctionStorageQueue(
                    queue_name="get-weather-input-queue",
                    queue_service_endpoint=STORAGE_QUEUE_ENDPOINT,
                )
            ),
            output_binding=AzureFunctionBinding(
                storage_queue=AzureFunctionStorageQueue(
                    queue_name="get-weather-output-queue",
                    queue_service_endpoint=STORAGE_QUEUE_ENDPOINT,
                )
            ),
            function=AzureFunctionDefinitionFunction(
                name="GetWeather",
                description="Get the current weather in a location.",
                parameters={
                    "type": "object",
                    "properties": {
                        "location": {"type": "string", "description": "The city or town."}
                    },
                    "required": ["location"],
                },
            ),
        )
    )

  2. Agent Version Registration: Attaches the tool to a prompt agent:

    def create_the_agent(project):
    agent = project.agents.create_version(
        agent_name="azure-function-agent-get-weather",
        definition=PromptAgentDefinition(
            model=MODEL,
            instructions="You are a helpful support agent. When asked about the weather, always use the GetWeather tool.",
            tools=[describe_the_tool()],
        ),
    )
    print(f"Created agent {agent.name}, version {agent.version}")
    return agent

  3. Agent Invocation via Responses API: Calls the agent with agent_reference:

    def ask(client, agent, question):
    print(f"\nYou: {question}")
    response = client.responses.create(
        input=question,
        extra_body={"agent_reference": {"name": agent.name, "type": "agent_reference"}},
    )
    print(f"Agent: {response.output_text}")

Knowledge check

1. What role does azure.yaml play in an azd project?
  • A. It is an alternative to Python virtual environments
  • B. It is the project manifest that maps application services to local source directories and defines their Azure hosting targets
  • C. It configures the user prompt instructions

Answer: B

azure.yaml tells azd where your application code is located (e.g. ./app/) and how to package and deploy it (e.g. host: function).

2. What is the purpose of the capability host in infra/main.bicep?
  • A. It generates API keys
  • B. It binds the Foundry project to customer-owned Storage, Search, and Cosmos DB, creating the Standard Setup required for queue tools
  • C. It compiles Python bytecode

Answer: B

The capability host transforms a project into a Standard Setup, enabling the Agent Service to interact with external storage queues.

3. Why must the Function output message include CorrelationId?
  • A. It is required by Python syntax
  • B. The Foundry Agent Service uses CorrelationId to match the asynchronous response from the queue to the pending conversation turn
  • C. It authenticates with Azure Functions

Answer: B

Because queues are asynchronous and decoupled, the CorrelationId is the only identifier linking the function reply to the agent's turn.
