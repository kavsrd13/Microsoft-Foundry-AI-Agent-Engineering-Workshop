# Production operations exercises

These exercises require a deployed workload, Application Insights access and an approved telemetry/data-retention policy. Local tests do not demonstrate operational coverage.

1. Run `observe.py` three times; query `operations.kql` in Application Insights. Compare count, p95 latency and token totals. Follow one trace ID across spans. For the complete web application, instrument request, retrieval, tool and model boundaries under the same trace; the one-call script teaches the token attributes only.
2. Trigger a controlled failure using an invalid deployment name, then restore it. Identify status, failed span, timestamp and affected dependency. Create a narrowly scoped alert in Azure Monitor for repeated failures, test its action group with the instructor's test destination, then disable/delete only that test alert. Do not send test notifications to production recipients.
3. Define an SLO worksheet: acceptable latency, error proportion, unsupported-answer rate, leakage count and time-to-detect stale data. Specify measurement window, minimum sample size, owner and response action.
4. Convert model token totals using the current deployment-specific input/output rates. Add Search, Cosmos, Functions/compute and telemetry costs. Use a dated currency/rate sheet; token telemetry alone is not the Azure bill. In Cost Management filter the lab resource group/tags, examine service meters and create an instructor-approved budget alert. A budget is an alert, not an automatic hard spending cap.
5. Keep evaluation types distinct: Lab11 provides built-in quality/safety evaluators; this lab provides a custom rubric and measured retrieval; evaluate the whole agent separately for tool selection, tool outcomes and task completion. Add labelled tool-use cases before claiming an agent evaluation suite covers them.
6. In Foundry's evaluation/monitoring view, select the deployed candidate and an approved evaluator, verify model/evaluator region, run a small synthetic batch, and inspect individual failures. Record run ID, candidate version, dataset version and evaluator configuration. If continuous evaluation is supported in the target tenant, configure a scoped sample, verify new results arriving and then disable the classroom configuration. Otherwise rerun the batch on a schedule through your approved pipeline; mark native continuous evaluation unavailable rather than simulated.
7. Production samples can contain citizen data. Define minimisation/redaction, retention and access before sampling. Prefer synthetic canaries for classroom production monitoring. Do not commit raw production prompts/answers to the repository.
8. Run the release gate before promotion. Reject missing/old results and reference-pipeline failures; additionally require app identity tests, deployment smoke tests and human review of severe cases. Test rollback to a previously approved artefact and record the previous revision.

Evidence: query export without user content, trace ID, alert test result, cost worksheet, evaluation run/version and rollback result. Pending steps stay pending.

Sources: [tracing](https://learn.microsoft.com/azure/foundry/observability/how-to/enable-tracing), [agent evaluation](https://learn.microsoft.com/azure/foundry/observability/how-to/evaluate-agent), [Azure Monitor alerts](https://learn.microsoft.com/azure/azure-monitor/alerts/alerts-overview), [Cost Management budgets](https://learn.microsoft.com/azure/cost-management-billing/costs/tutorial-acm-create-budgets).
