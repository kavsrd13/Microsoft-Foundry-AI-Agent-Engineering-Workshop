Retrieve from a knowledge base with Foundry IQ

Foundry IQ sits above a search index: you register knowledge sources, group them into a knowledge base, and retrieve against that base rather than writing your own query plan.

This exercise deliberately calls the REST endpoint directly with urllib, so you can see the API version, the Entra scope and the exact request body rather than having them hidden behind a helper. It also draws a clear line between the GA extractive path and the preview planning and synthesis path.

This exercise takes approximately 45 minutes.

Note: Some of the technologies used in this exercise are in preview or in active development. You may experience some unexpected behavior, warnings, or errors. All data used in this exercise is synthetic; do not substitute real records.

Lab folder: day3-foundry-sdk-enterprise/lab09-foundry-iq
Run scripts from: the lab folder (not from src)

Before you start

What you will do

  • Distinguish a knowledge source from a knowledge base.
  • Call the GA retrieval endpoint with an Entra bearer token.
  • Compare GA extractive retrieval with preview planning and synthesis.
  • Fall back to a plain Search query when IQ is unavailable, and label it honestly.

Prerequisites

  • An Azure AI Search service in a region where the knowledge base capability is available.
  • Search Service Contributor and Search Index Data Contributor.
  • A Foundry project. Preview planning additionally requires permission to use preview features — confirm before enabling it.

Caution: Availability varies by region and changes over time. Verify the capability in your project before scheduling this exercise, and use the fallback path described below if it is absent. An unavailable feature is a finding to record, not a step to skip silently.

Set up and create the knowledge objects

  1. cd day3-foundry-sdk-enterprise/lab09-foundry-iq
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
az login

  2. Fill in .env. Note that this exercise uses MODEL_DEPLOYMENT_NAME and SEARCH_INDEX_NAME, not the shorter names used on Day 1:

    PROJECT_ENDPOINT=https://<account>.services.ai.azure.com/api/projects/<project>
MODEL_DEPLOYMENT_NAME=<deployment-name>
SEARCH_ENDPOINT=https://<search-name>.search.windows.net
KNOWLEDGE_BASE_NAME=<your-lab09-knowledge-base>
SEARCH_INDEX_NAME=<your-lab09-index>

    Tip: Environment variable names differ between exercises because they mirror the SDK sample each one is based on. Always copy the .env.example from the exercise you are running rather than reusing a previous .env.

  3. Follow data/portal-walkthrough.md to create an isolated knowledge source and knowledge base over the synthetic files in this lab. Give them names you will recognise as yours.

    Note: A knowledge source is a connection to content. A knowledge base groups one or more sources into a single retrieval target. You query the base, not the source.

  4. Upload the synthetic documents into your index:

    python src/upload.py

    Each record is labelled citizen-service, so the fallback query later has something to filter on.

Call the GA retrieval endpoint

Open src/retrieve.py. It is intentionally written with urllib rather than an SDK client so the whole HTTP contract is visible.

  1. Look at how the token is acquired and scoped:

    token = credential.get_token('https://search.azure.com/.default').token

    The audience is the Search service, not Microsoft Graph and not the model API. Requesting the wrong scope is a common cause of a confusing 401.

  2. Look at the URL and the GA request body:

    url = f"{endpoint}/knowledgebases/{kb_name}/retrieve?api-version=2026-04-01"
body = {'intents': [{'type': 'semantic', 'search': question}]}

    The GA shape uses intents and returns extractive evidence — passages drawn from your documents, with references.

  3. Run it:

    python src/retrieve.py

    The full JSON response is printed and saved to data/live-retrieval.json. Read the references section: those identify which documents supported the result. That is the evidence trail, and it is what distinguishes retrieval from generation.

Compare the preview planning path

  1. Check first that you are permitted to use preview features in this project. If not, stop here and record that.

  2. The preview path changes both the API version and the request shape:

    version = '2026-08-01-preview'
body = {'messages': [{'role': 'user', 'content': [{'type': 'text', 'text': question}]}]}

    A message-shaped request rather than an intent-shaped one, because the service is now planning queries and synthesising an answer rather than returning passages.

  3. python src/retrieve.py --preview

  4. Compare the two responses side by side and write down the difference that matters: the GA path gives you evidence you must assemble; the preview path gives you a synthesised answer plus activity showing how it got there. The second is more convenient and has more to verify.

    Caution: Do not build a production commitment on a preview API version without confirming its current status and your organisation's position on preview features.

Use the fallback and label it accurately

If the knowledge base capability is unavailable in your region or project, you can still complete the retrieval concept using plain Search.

  1. python src/search_fallback.py

    results = client.search('leave travel', top=3,
    filter="allowed_groups/any(g: search.in(g, 'citizen-service'))")

    This is ordinary text retrieval with the same application-enforced group filter you built in Exercise 08.

  2. Be precise about what this demonstrates. It shows retrieval and access filtering. It does not show agentic query planning, which is the thing Foundry IQ adds.

  3. Open data/illustrative-output.md. This file exists so that a classroom without the capability still has something to discuss.

    Caution: It is clearly labelled an illustration. It is not a recording of a successful service call, and it must never be presented as evidence that the feature ran. Capture your own sanitised output if you need real evidence.

  4. Run the local checks:

    python validate.py
python validate.py --live

    Note: The --live flag here checks that a saved artefact exists and is non-empty after you ran a real retrieval. It does not itself call Azure.

Knowledge check

Answer each question, then expand it to check yourself.

1. Which retrieval input does the GA path in this exercise use?
  • A. intents
  • B. messages
  • C. tool_calls

Answer: A

messages is the preview planning shape; intents is the GA extractive shape.

2. Which capability is preview in this exercise?
  • A. Text search
  • B. Query planning and answer synthesis
  • C. Entra authentication

Answer: B

Extractive retrieval is GA. Planning and synthesis are behind the preview API version.

3. What identifies the evidence supporting a retrieval result?
  • A. The length of the response
  • B. The generated answer text alone
  • C. The source references in the response

Answer: C

References are what let a reviewer trace an answer back to a document.

Summary

You created a knowledge source and base, retrieved against it through the GA REST endpoint with a correctly scoped Entra token, and compared extractive retrieval with preview planning and synthesis.

You also practised the discipline this workshop applies throughout: when a capability is unavailable, use the labelled fallback and record the limitation rather than marking an unrun step as passed.

Delete data/live-retrieval.json if it contains output you do not wish to retain.
