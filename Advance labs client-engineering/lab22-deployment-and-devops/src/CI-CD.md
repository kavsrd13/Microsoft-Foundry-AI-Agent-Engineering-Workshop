# OIDC, evaluation and environment promotion

Copy `workflow.yml` to the repository root `.github/workflows/resident.yml`. It assumes this repository contains `foundry-agent-workshop/client-engineering/`; if the workshop itself is your repository root, remove `foundry-agent-workshop/` from all workflow paths. The distributed template does not activate CI by itself.

1. Provision separate dev, test and prod footprints using the README. Use different azd environment names and Entra registrations. Keep a deployment inventory with environment, resource group, app names, Search index and project endpoint.
2. Create GitHub environments `dev`, `test`, `prod`; restrict deployment branches to your reviewed release branch. Add required reviewers for test/prod as supported by your repository plan. Use a separate deployment service principal per environment and a federated credential with issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, subject `repo:OWNER/REPOSITORY:environment:dev` (repeat with test/prod). No client secret is required. [OIDC configuration](https://learn.microsoft.com/azure/developer/github/connect-from-azure-openid-connect)
3. Assign deployment identity Website Contributor only on that environment's two existing web/function resources. Grant its evaluation identity the required Foundry inference and Search Index Data Reader roles on the evaluation resources. This code-deployment workflow cannot provision infrastructure or grant roles; perform reviewed IaC changes separately.
4. In **each** GitHub environment configure variables `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `WEB_APP_NAME`, `FUNCTION_APP_NAME`, `PROJECT_ENDPOINT`, `MODEL_DEPLOYMENT`, `JUDGE_DEPLOYMENT`, `SEARCH_ENDPOINT`, `SEARCH_INDEX`. The final six point to a prepared Lab23 evaluation fixture compatible with that environment, not an empty newly provisioned Search service. Keep fixture ACLs and IDs consistent with Lab23. Provision a judge deployment if different from chat.
5. Dispatch `dev` for a reviewed commit. The immutable `github.sha` is used by checkout, evaluation, gate and artifact name. Offline web tests use a separate virtual environment from Lab23 because their Search SDK versions differ. A failing evaluation prevents both deployment steps.
6. Run live app smoke/access tests and record the SHA. Dispatch `test`, then `prod` **at the same commit/ref**, selecting the corresponding GitHub environment and obtaining required reviews. Reruns evaluate target-specific configuration. The example does not automatically prove that a SHA passed an earlier environment: reviewers must verify the successful prior run and live evidence. A production extension can enforce that attestation.
7. Roll back by dispatching a previously verified commit with its matching configuration/index schema, rerunning the gate. Model, index and schema compatibility must be checked; code rollback does not undo data changes.

The workflow evaluates the reference RAG implementation in Lab23, not the deployed Lab21 HTTP app. Its mocked JWT/SSE tests are necessary but do not replace real Entra and two-user access tests. The provided workflow intentionally deploys existing infrastructure only. Build Bicep and review ARM what-if through an approved provisioning identity before any infrastructure promotion. `azd env new resident-test` and the README settings reproduce the footprint; seed each environment independently with approved data.

For an evaluation-gate rejection exercise, change a candidate prompt in Lab23 to answer without evidence, run the workflow in dev, observe the failed gate and absent deployment, then restore it. Do not weaken the threshold to make a bad candidate pass.
