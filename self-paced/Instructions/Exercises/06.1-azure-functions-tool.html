Exercise 06.1 — Host an Azure Functions tool for a Foundry agent (queue-based)

In this exercise, you connect a Microsoft Foundry agent to a serverless Azure Function using Azure Storage queues. Instead of your client code calling an HTTP endpoint, the Foundry Agent Service itself drops tool requests onto an Azure Storage queue, your serverless Function processes the request, and the answer is returned through an output queue.

This provides scale-to-zero serverless hosting, automatic retries, and clean security isolation without managing API keys or connection strings.

This exercise takes approximately 60–75 minutes.

Lab folder: labs/06.1-azure-functions-tool
Run scripts from: the lab folder
Environment: azure-ai-projects>=2.0.0, azure-identity, Azure Developer CLI (azd)

Before you start

Prerequisites

  • Python 3.10 or 3.11 installed.
  • Azure CLI installed and signed in (az login).
  • Azure Developer CLI (azd) installed (verify with azd version).
  • An active Azure subscription with permissions to create resources and assign roles.

Task 1: Sign in and initialize the project template

Start by opening a terminal and authenticating with Azure.

  1. Navigate to the lab directory:

    cd labs/06.1-azure-functions-tool

  2. Sign in with the Azure CLI, and configure azd to reuse your login credentials:

    az login
azd config set auth.useAzCliAuth true
azd auth login --check-status

    Check: Output confirms Logged in to Azure as you@yourdomain.com.

  3. Initialize the project template using the official Microsoft template command:

    azd init --template azure-functions-ai-services-agent-python

    What this does: azd connects to Microsoft's GitHub repository (Azure-Samples/azure-functions-ai-services-agent-python) and downloads the template files directly into your folder.

    When prompted for an environment name, enter:

    azfn-agent-lab

    Note: In this workshop repository, these template files (azure.yaml, infra/, app/) are already pre-loaded in labs/06.1-azure-functions-tool. If prompted to overwrite existing files, select Keep my existing files or run azd env new azfn-agent-lab.

Task 2: Understand the template files (YAML and Bicep)

Now that the template is initialized, look at what was downloaded to understand how everything connects.

1. azure.yaml — The Project Manifest

Open azure.yaml in the root of the lab folder:

# yaml-language-server: $schema=https://raw.githubusercontent.com/Azure/azure-dev/main/schemas/v1.0/azure.yaml.json
name: azure-functions-tool-lab
services:
  api:
    project: ./app/
    language: python
    host: function
  • name: The name of this azd application.
  • services.api: Tells azd that there is an application service named api.
  • project: ./app/: Points to the directory containing your Python Function code.
  • host: function: Tells azd that this code should be packaged and deployed to an Azure Function App.

2. infra/main.bicep — The Cloud Infrastructure

Open infra/main.bicep. This Infrastructure-as-Code file creates the entire Standard Setup environment in Azure:

  • Azure AI Foundry Services Account & Project: The cloud workspace where your agent lives.
  • Model Deployment: Deploys a chat model (e.g. gpt-5.1 or gpt-4.1-mini).
  • Azure Storage Account with 2 Queues: Automatically creates get-weather-input-queue and get-weather-output-queue.
  • Flex Consumption Function App: Serverless compute with scale-to-zero pricing to host your custom tool.
  • Capability Host: Binds the project to your storage queues. (This capability host is what makes it a Standard Setup).
  • RBAC Roles: Grants Storage Queue Data Contributor to the Foundry Project identity and the Function App identity so they can communicate securely without passwords.

3. app/function_app.py — The Serverless Tool

Open app/function_app.py. Notice how the function communicates via queues rather than HTTP:

import json
import logging
import azure.functions as func

app = func.FunctionApp()

INPUT_QUEUE = "get-weather-input-queue"
OUTPUT_QUEUE = "get-weather-output-queue"

# Triggered whenever the agent drops a message on the input queue
@app.function_name(name="GetWeather")
@app.queue_trigger(arg_name="msg", queue_name=INPUT_QUEUE, connection="STORAGE_CONNECTION")
@app.queue_output(arg_name="reply", queue_name=OUTPUT_QUEUE, connection="STORAGE_CONNECTION")
def get_weather(msg: func.QueueMessage, reply: func.Out[str]) -> None:
    raw = msg.get_body().decode("utf-8")
    logging.info("Message from agent: %s", raw)

    request = json.loads(raw)
    arguments = request.get("function_args") or request
    location = arguments.get("location", "an unknown place")

    # Custom business logic (e.g., API call or database query)
    weather = f"It is {len(location) + 10} degrees and sunny in {location}."

    # CRITICAL: CorrelationId must be returned in the response!
    answer = {
        "Value": weather,
        "CorrelationId": request["CorrelationId"],
    }
    reply.set(json.dumps(answer))
    logging.info("Reply to agent: %s", json.dumps(answer))

Critical Requirement: Notice line "CorrelationId": request["CorrelationId"]. The agent uses this ID to match the function's reply to the question it asked. If you omit it, the agent will never acknowledge the reply and will time out.

Task 3: Provision cloud resources with azd provision

Now deploy the cloud infrastructure defined in the Bicep templates.

  1. Configure the target Azure region for your environment:

    azd env set AZURE_LOCATION australiaeast

    Tip: australiaeast, eastus2, and swedencentral are supported regions with model quota and Flex Consumption availability.

  2. Run azd provision to build the entire cloud environment:

    azd provision

    What happens: azd compiles the Bicep files, creates the Azure Resource Group, provisions the Foundry project, model deployment, Storage queues, and Function App, and configures all RBAC permissions automatically.

    Note: Provisioning takes approximately 10 to 12 minutes.

    Check: Output reports SUCCESS: Your application was provisioned in Azure in ....

  3. View the captured deployment outputs:

    azd env get-values

  4. Create your local .env file from the template:

    Copy-Item .env.example .env

    Open .env and fill in the values printed by azd env get-values:

    PROJECT_ENDPOINT=https://your-resource.services.ai.azure.com/api/projects/your-project
STORAGE_QUEUE_ENDPOINT=https://your-storage-account.queue.core.windows.net
MODEL_DEPLOYMENT=gpt-5.1

Task 4: Deploy the Function code with azd deploy

Now that the cloud infrastructure exists, upload your Python function code.

  1. Deploy the function code to the newly created Flex Consumption Function App:

    azd deploy

    What happens: azd reads azure.yaml, packages the ./app/ folder, uploads it to Azure, and triggers a remote build to install dependencies and activate the queue listener.

    Check: Output confirms SUCCESS: Your application was deployed to Azure.

  2. Verify that Azure Functions registered the queue trigger:

    az functionapp function list -g rg-azfn-agent-lab -n YOUR_FUNCTION_APP_NAME --query "[].{name:name, trigger:config.bindings[0].type}" -o table

    Check: You should see GetWeather with trigger type queue.

Task 5: Run the Python agent and test the tool

Now run the agent script that tells Foundry to use this Function as a tool.

  1. Set up a Python virtual environment and install dependencies:

    py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

  2. Inspect ask_the_agent.py. Notice how AzureFunctionTool is defined:

    # Define the tool pointing to the input and output queues
tool = AzureFunctionTool(
    azure_function=AzureFunctionDefinition(
        input_binding=AzureFunctionBinding(
            storage_queue=AzureFunctionStorageQueue(
                queue_name="get-weather-input-queue",
                queue_service_endpoint=STORAGE_QUEUE_ENDPOINT,
            )
        ),
        output_binding=AzureFunctionBinding(
            storage_queue=AzureFunctionStorageQueue(
                queue_name="get-weather-output-queue",
                queue_service_endpoint=STORAGE_QUEUE_ENDPOINT,
            )
        ),
        function=AzureFunctionDefinitionFunction(
            name="GetWeather",
            description="Get the current weather in a location.",
            parameters={
                "type": "object",
                "properties": {
                    "location": {"type": "string", "description": "The city or town."}
                },
                "required": ["location"],
            },
        ),
    )
)

# Create the agent with the tool attached
agent = project.agents.create_version(
    agent_name="azure-function-agent-get-weather",
    definition=PromptAgentDefinition(
        model=MODEL,
        instructions="You are a helpful support agent. When asked about the weather, use the GetWeather tool.",
        tools=[tool],
    ),
)

  3. Run the script:

    python ask_the_agent.py

    Observed Output:
    Created agent azure-function-agent-get-weather, version 1

    You: What is the weather like in Sydney right now?
    Agent: It's currently 16°C and sunny in Sydney.
    (took 42.1s including the queue round-trip)

    You: And in Melbourne?
    Agent: It's currently 19°C and sunny in Melbourne.
    (took 8.2s including the queue round-trip)

    Deleted azure-function-agent-get-weather version 1

    How you know the tool ran: In function_app.py, the function calculates len(location) + 10. "Sydney" has 6 letters (16°C) and "Melbourne" has 9 letters (19°C). Those numbers came from your serverless function code, not the LLM!

Task 6: Clean up resources

When you are finished testing, delete the provisioned Azure resources to avoid ongoing costs. The --purge option permanently deletes the AI Services account to immediately release model quota:

azd down --purge --no-prompt

Check: Output confirms all Azure resources have been deleted.

Knowledge check

1. What does the azd init --template command do?
  • A. Installs Python packages
  • B. Clones a repository template containing azure.yaml, Bicep infrastructure files, and application code into your directory
  • C. Creates an Azure subscription

Answer: B

azd init initializes your project from a starter template repository on GitHub.

2. Why is the CorrelationId required in the Function's queue response?
  • A. To authenticate with Azure
  • B. So the Foundry Agent Service can match the asynchronous queue reply to the pending tool call turn
  • C. To format the temperature units

Answer: B

Because queue communication is asynchronous, CorrelationId is the only token that connects the function answer back to the agent's question.

3. Why must we use the --purge flag when running azd down?
  • A. To speed up the deletion
  • B. To permanently delete the AI resource and recover regional token-per-minute (TPM) model quota
  • C. To delete the local virtual environment

Answer: B

Azure AI Services has soft-delete enabled by default. The --purge flag permanently clears it so your quota is restored immediately.
