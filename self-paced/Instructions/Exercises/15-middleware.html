Intercept agent, model and tool calls with middleware

Middleware is where cross-cutting concerns belong: logging, redaction, policy enforcement and short-circuiting. In this exercise you register middleware at three distinct boundaries and watch the order in which they fire.

You will also block a request before any model or tool call happens, which is the cheapest and safest place to enforce a policy — nothing is sent anywhere, so nothing can leak and nothing is billed.

This exercise takes approximately 45 minutes.

Note: Some of the technologies used in this exercise are in preview or in active development. You may experience some unexpected behavior, warnings, or errors. All data used in this exercise is synthetic; do not substitute real records.

Understand the three boundaries

Open src/demo.py. Four middleware classes are defined, and where each is registered is as important as what it does.

  1. ClassBaseWrapsRegistered on
    RunLogAgentMiddlewareThe whole agent runThe agent
    BlockExportAgentMiddlewareThe whole agent runThe agent
    ModelLogChatMiddlewareEach model callThe chat client
    ToolLogFunctionMiddlewareEach tool invocationThe chat client

  2. Every one has the same shape — work before, await call_next(), work after:

    class ToolLog(FunctionMiddleware):
    async def process(self, context, call_next):
        print('3 TOOL before:', context.function.name)
        await call_next()
        print('4 TOOL after')

    call_next() is the rest of the pipeline. What you do before it sees the request; what you do after it sees the result; and whether you call it at all decides if the operation happens.

Trace the call order

  1. python src/demo.py

    The first request asks for an order's status and total, which requires tool calls.

  2. Read the numbered console output. The numbers are boundary labels, and the nesting tells you the structure: a RUN surrounds everything; MODEL pairs surround each inference; TOOL pairs surround each function.

  3. Count the MODEL pairs. There will usually be more than one inside a single RUN, because the agent calls the model, receives tool requests, runs the tools, then calls the model again with the results.

    Note: The labels are numbered 1 to 6 for readability, but do not expect a flat 1-2-3-4-5-6 trace. The real sequence depends on how many tools the model decides to call.

Block a request before it costs anything

  1. Read BlockExport. It sets a result and **returns without calling call_next()**:

    class BlockExport(AgentMiddleware):
    async def process(self, context, call_next):
        if any('export all' in m.text.lower() for m in context.messages):
            context.result = AgentResponse(
                messages=[Message('assistant', ['Bulk export is disabled in this demo.'])])
            print('BLOCK: call_next was not called; no model or tool call.')
            return
        await call_next()

  2. The second request in the demo is Export all orders. In the output, confirm that the BLOCK line appears and that no MODEL or TOOL lines appear for that request — while the outer RUN pair still completes normally.

    Check: No model call means no tokens billed, no data sent to the model, and no tool executed. This is the cheapest possible enforcement point.

  3. Compare this with filtering an answer after generation. By then the model has already seen the data and produced text, and you are relying on catching it. Blocking first avoids the question entirely.

Redact logs, and see what redaction does not do

  1. RunLog redacts email addresses from what it prints:

    text = ' '.join(m.text for m in context.messages)
print('1 RUN before:',
      re.sub(r'[\w.+-]+@[\w.-]+\.[A-Za-z]{2,}', '[EMAIL REDACTED]', text))

  2. The first request contains learner@acme.com.au. Confirm it appears as [EMAIL REDACTED] in the console.

  3. Now the important part. The email still reached the model. The middleware redacted the log line, not the request.

    Caution: Log redaction and data minimisation are different controls. If the address must not reach the model, remove it from the message before call_next() — not from the string you print.

  4. Note also that the middleware deliberately does not print tool arguments, tool results or model responses. Logging everything 'for debugging' is how sensitive content ends up in a log store with weaker access controls than the system it came from.

  5. Test the regex honestly. Try a request containing an address the pattern misses.

    Caution: A regex is an illustration, not a PII detector. Real redaction needs a purpose-built classifier and a policy about what is collected in the first place.

Knowledge check

Answer each question, then expand it to check yourself.

1. What happens if middleware sets a result and does not call call_next()?
  • A. The run short-circuits and returns that result
  • B. The request is retried
  • C. A second agent is created

Answer: A

No model or tool call occurs, so nothing is sent and nothing is billed.

2. Which middleware type surrounds a tool invocation?
  • A. Chat middleware
  • B. Function middleware
  • C. Session middleware

Answer: B

Chat middleware wraps model calls; agent middleware wraps the whole run.

3. Does redacting an email in the log remove it from what the model received?
  • A. Yes
  • B. No
  • C. Only on Windows

Answer: B

The redaction applies to the printed string. The original message was still sent.

Summary

You registered middleware at the agent, model and tool boundaries, traced the real call order including multiple model round-trips inside one run, short-circuited a request before any inference occurred, and redacted PII from logs.

You also drew the line between log redaction and data minimisation — a distinction that matters as soon as real personal information is involved.
