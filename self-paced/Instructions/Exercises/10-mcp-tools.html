Connect an MCP server and approve every tool call explicitly

The Model Context Protocol lets an agent discover and call tools hosted by a separate server. In this exercise you attach the public Microsoft Learn MCP server to a Responses request and run the approval loop.

The emphasis is on control. You will restrict the agent to one named tool, require approval for every call, deny the first request to prove denial works, and only then approve one. An MCP tool call sends your query to a third-party server, which is a data-egress decision and deserves to be treated as one.

This exercise takes approximately 45 minutes.

Note: Some of the technologies used in this exercise are in preview or in active development. You may experience some unexpected behavior, warnings, or errors. All data used in this exercise is synthetic; do not substitute real records.

Read the five fields that define the connection

Open src/demo.py. The entire MCP configuration is one dictionary, and every key in it is a control.

  1. tools = [{'type': 'mcp',
          'server_label': 'microsoft_learn',
          'server_url': 'https://learn.microsoft.com/api/mcp',
          'allowed_tools': ['microsoft_docs_search'],
          'require_approval': 'always'}]
    • type: 'mcp' — this is a hosted tool the service connects to, not a function your application executes.
    • server_url — a fixed, known endpoint. It is not discovered at runtime and not model-supplied.
    • server_label — the name used in approval requests, so you can tell servers apart.
    • allowed_tools — an allowlist. The server may offer many tools; this request permits exactly one.
    • require_approval: 'always' — nothing executes without your explicit decision.

    Note: Two independent controls are at work: the allowlist bounds what could be called, and approval governs whether it is. Relying on only one of them is weaker than it looks.

Deny a call, then approve one

  1. Run the demo:

    python src/demo.py

  2. You will be shown the server label, the tool name and the arguments the model wants to send. Read the arguments — that text is what will leave your environment.

    while approvals := [item for item in response.output
                   if item.type == 'mcp_approval_request']:
    for item in approvals:
        print(item.server_label, item.name, item.arguments)
        permitted = (item.server_label == 'microsoft_learn'
                     and item.name == 'microsoft_docs_search')
        approved = permitted and input('Approve this public documentation query? [y/N] ').lower() == 'y'

    Tip: Note the belt-and-braces check: the application re-verifies the server and tool name itself before even offering you the prompt. It does not rely solely on the service having honoured allowed_tools.

  3. **Type n on this first run.** The decision is returned with approve: False and the tool does not execute. Confirm from the final answer that no documentation content was used.

    Check: A denied call must produce no tool result. If it did, the control would be decorative.

  4. Run it again and type y this time. The continuation sends the decision correlated by approval_request_id:

    decisions.append({'type': 'mcp_approval_response',
                  'approval_request_id': item.id,
                  'approve': approved})

    Just as call_id correlated function results in Exercise 05, approval_request_id is what ties a decision to the specific request it answers.

  5. Compare the two answers. The approved run should cite documentation content; the denied run should not. The real output is saved to data/live-output.txt.

  6. Note that the loop is a while, not an if. A single turn can produce several approval rounds, and the loop never auto-approves a later one just because you approved the first.

Think about the egress decision

  1. This tool is read-only, which feels safe. But consider the direction of the risk: the query travels outward. If a user's question contained case details, approving the call would send those details to a third-party server.

    Caution: 'Read-only' describes what the tool does to the remote system. It says nothing about what your data does on the way there.

  2. List in your notes what you would require before allowing an MCP server in production: a known and reviewed endpoint, an allowlist of tools, an approval or policy gate, a record of what was sent, and an assessment of where that data lands.

  3. Exercise 20 builds the other half of this picture: your own MCP server, hosted locally, wrapping an authenticated internal tool.

Knowledge check

Answer each question, then expand it to check yourself.

1. What happens before an allowed MCP call executes in this exercise?
  • A. Automatic consent
  • B. Explicit approval
  • C. A new role assignment

Answer: B

require_approval: 'always' means each invocation waits for a decision you make.

2. Can a read-only tool still disclose data?
  • A. Yes — the query itself is sent to the server
  • B. No, reads are always safe
  • C. Only if an API key is used

Answer: A

Egress is about what you send, not only what you receive.

3. What links an approval decision to the request it answers?
  • A. The deployment name
  • B. The order of the decisions
  • C. approval_request_id

Answer: C

The same correlation pattern as call_id in Exercise 05.

Summary

You attached a remote MCP server to a Responses request, restricted it to a single allowed tool, required approval for every call, denied one invocation to prove denial works, and approved another.

You also identified the real risk in a read-only tool: the outbound query. Exercise 20 has you host an MCP server of your own in front of an authenticated internal API.
