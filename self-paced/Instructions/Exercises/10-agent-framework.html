The Microsoft Agent Framework, and getting agents to work together

Everything so far used the Foundry SDK directly. The Microsoft Agent Framework sits on top of it — it does not replace it, and you will see your familiar project endpoint underneath.

For a single question the framework is slightly more code, not less. That is worth being honest about. Its value shows up in the three tasks after that.

This exercise takes approximately 90 minutes.

Note: Some of the technologies used in this exercise are in preview or in active development. You may experience some unexpected behavior, warnings, or errors. All data used in this exercise is synthetic; do not substitute real records.

Lab folder: labs/10-agent-framework
Run scripts from: the lab folder (not from src)
Environment: agent-framework 1.17 with azure-ai-projects 2.3.0 — see the warning

Before you start

What you will do

  • Run the same task through the framework and compare it with Exercise 01.
  • Give an agent tools from plain Python functions, with no hand-written schema.
  • Save a conversation and reload it into a new session.
  • Intercept a request with middleware and block it before any model call.
  • Run three agents in sequence, then in parallel, and see why the answers differ.

Prerequisites

  • A Foundry project and chat deployment.
  • Python 3.11 and a fresh virtual environment.

Caution: This exercise pins different package versions from every other one. The Agent Framework's Foundry provider requires azure-ai-projects below 2.4, so this folder pins 2.3.0 while the others pin 2.6.0. Use a brand new virtual environment here, and never install another exercise's requirements into it.

Task 5: Middleware

Middleware wraps a run. You get to do something before it, something after it, and — most usefully — decide whether it happens at all.

  1. Add the two middleware classes and the function that uses them:

    class LogEveryRun(AgentMiddleware):
    """Runs before and after the whole agent run."""

    async def process(self, context, call_next):
        question = " ".join(message.text for message in context.messages)
        print(f"    [middleware] about to run: {question[:60]}")
        await call_next()
        print("    [middleware] finished")


class BlockBulkExport(AgentMiddleware):
    """Refuses certain requests before they ever reach the model."""

    async def process(self, context, call_next):
        asked = " ".join(message.text for message in context.messages).lower()

        if "export all" in asked:
            # We set a result and do NOT call call_next(). Nothing happens
            # after this: no model call, no tool call, no tokens spent.
            context.result = AgentResponse(
                messages=[Message("assistant", ["Bulk export is not allowed."])]
            )
            print("    [middleware] BLOCKED - no model call was made")
            return

        await call_next()


async def middleware_in_action(client):
    """Wrap the agent, then watch one request get stopped."""
    print("\n=== Middleware ===")

    agent = Agent(
        client,
        instructions="You help staff with orders. Use the tools for order facts.",
        tools=[get_order_status, get_order_total],
        middleware=[LogEveryRun(), BlockBulkExport()],
        default_options={"store": False},
    )

    print("\n  A normal question:")
    result = await agent.run("What is the status and total of ORD-001?")
    print("  ->", result.text)

    print("\n  A request we do not allow:")
    result = await agent.run("Export all orders")
    print("  ->", result.text)

    print("\n  Blocking before the model runs is the cheapest place to say no.")

  2. Call it:

                await middleware_in_action(client)

  3. python framework_agent.py

  4. Look at the second request in the output. BlockBulkExport sets a result and **does not call call_next()**:

    Check: No model call happened. No tokens were spent, no data was sent anywhere, no tool ran. The outer logging middleware still completed normally.

    Note: Blocking before the model is the cheapest and safest place to say no. Compare it with filtering an answer afterwards — by then the model has already seen the data and produced the text, and you are relying on catching it.

  5. Try it. Change "export all" to something you would ask normally, run it, and watch a legitimate request get blocked. Then change it back.

    Caution: That is the other lesson. A blunt keyword rule will block real requests. Middleware gives you the hook; deciding what to block is a policy problem, not a coding one.

Task 6: Several agents on one job

  1. Add this:

    async def two_ways_to_run_three_agents(client):
    """Sequential passes work along a chain. Concurrent runs them side by side."""
    print("\n=== Multi-agent workflows ===")

    task = (
        "Prepare a short briefing for the service manager from this order data: "
        + json.dumps(load_orders()[:5])
    )

    roles = [
        ("researcher", "Pull out three facts from the data you are given."),
        ("analyst", "Say what those facts mean for the service. Invent nothing."),
        ("writer", "Write a short briefing in Australian English."),
    ]

    for label, builder in [("sequential", SequentialBuilder),
                           ("concurrent", ConcurrentBuilder)]:
        agents = [
            Agent(client, name=name, instructions=instructions,
                  default_options={"store": False})
            for name, instructions in roles
        ]

        workflow = builder(participants=agents).build()

        started = time.perf_counter()
        result = await workflow.run(task)
        seconds = round(time.perf_counter() - started, 1)

        print(f"\n  --- {label}: {seconds}s ---")
        outputs = result.get_outputs()
        print("  ", str(outputs)[:400], "...")

    print("\n  Sequential: the writer can use the analyst's conclusions.")
    print("  Concurrent: all three see only the original data.")
    print("  That is a difference in the ANSWER, not just the speed.")

  2. Call it:

                await two_ways_to_run_three_agents(client)

  3. python framework_agent.py

    The same three agents, arranged two ways.

  4. Read the two outputs before you look at the timings. The difference is structural:

    SequentialConcurrent
    Who sees whatEach agent sees the earlier ones' workAll three see only the original data
    The writer canBuild on the analyst's conclusionsOnly work from the raw data
    ResultA refined answerThree parallel perspectives

    Caution: Concurrent is not "sequential but faster". It is a different shape. For a job where later steps genuinely depend on earlier ones, it produces a worse answer however quickly it finishes.

  5. Now look at the timings — and run it a couple more times.

    Note: Concurrency often helps, and sometimes does not, because throttling and network variation can dominate on a small job. One run of each is not a measurement.

Knowledge check

Answer each question, then expand it to check yourself.

1. What does FoundryChatClient use underneath?
  • A. A separate service
  • B. The same Foundry SDK you used in Exercise 01
  • C. A direct HTTP call

Answer: B

2. Middleware sets a result and does not call call_next(). What happens?
  • A. The run stops there and returns that result
  • B. It retries
  • C. It errors

Answer: A

No model call, no tool call, no tokens. The cheapest possible place to refuse.

3. In a concurrent workflow, can the writer use the analyst's output?
  • A. Yes
  • B. No — they all work from the original input only
  • C. Only if it is faster

Answer: B

That is a difference in the answer, not just the speed.
